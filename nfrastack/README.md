# Nfrastack DB Backup

Контейнер для автоматических дампов базы данных.

Образ: `nfrastack/db-backup:4.9.2`. Модуль и сервис: `nfrastack`, контейнер: `nfrastack-container`.

## Быстрый старт

Из папки `nfrastack`:

1. Выполни `make env`.
2. Заполни `.env`: сеть, подключения к БД, UID/GID пользователя сервера (`id -u`, `id -g`).
3. Выполни `make init`: создаст сеть при необходимости, скачает образ и запустит контейнер.
4. Выполни `make backup-job JOB=01` и проверь дамп в `backup`.

Из корня проекта: `make nfrastack` для инициализации, `make -C nfrastack backup` для бэкапа.

## Настройка `.env`

Перед первым запуском отредактируй `.env`:

| Переменная | Описание                                                 |
|---|----------------------------------------------------------|
| `PROJECT_NAME` | Название проекта Docker Compose                          |
| `DB_BACKUP_VERSION` | Проверенная версия образа: `4.9.2` |
| `NETWORK` | Имя внешней Docker-сети, к которой подключается контейнер |
| `TIMEZONE` | Часовой пояс контейнера                                  |
| `DEFAULT_BACKUP_LOCATION` | Куда сохранять бэкапы, сейчас `FILESYSTEM`               |
| `DEFAULT_FILESYSTEM_PATH` | Путь внутри контейнера для дампов, сейчас `/backup`      |
| `DEFAULT_BACKUP_INTERVAL` | Интервал автоматического бэкапа в минутах                |
| `DEFAULT_BACKUP_BEGIN` | Время первого запуска в формате `HHMM`, например `0300`  |
| `DEFAULT_CLEANUP_TIME` | Через сколько минут удалять старые дампы                 |
| `DEFAULT_COMPRESSION` | Сжатие дампов, например `GZ`                             |
| `DEFAULT_MYSQL_SINGLE_TRANSACTION` | Консистентный дамп InnoDB, сейчас `TRUE` |
| `CONTAINER_ENABLE_MONITORING` | Мониторинг Zabbix; без Zabbix оставь `FALSE` |
| `CONTAINER_USER_DBBACKUP` | UID владельца дампов, например `1000` |
| `CONTAINER_GROUP_DBBACKUP` | GID владельца дампов, например `1000` |
| `DB01_TYPE` | Тип базы данных, например `mysql`, `pgsql`                      |
| `DB01_HOST` | Хост базы данных внутри Docker-сети                      |
| `DB01_PORT` | Порт базы данных                                         |
| `DB01_NAME` | Имя базы или `ALL`; в 4.x включает также `mysql` и `sys` |
| `DB01_USER` | Пользователь базы данных                                 |
| `DB01_PASS` | Пароль пользователя базы данных                          |
| `DB01_SPLIT_DB` | `TRUE` — сохранять базы отдельными файлами               |

Задания нумеруются подряд: `DB01_*`, `DB02_*` и т.д., без пропусков.
Настройки по умолчанию: ежедневно в `03:00`, интервал `1440` минут, хранение `43200` минут (30 дней).
После изменения `.env` выполни `make up`, чтобы Compose пересоздал контейнер с новым окружением.

## Данные

- `./backup` — дампы баз данных
- `./logs` — логи контейнера

Обе папки не хранятся в git.
Контрольные суммы находятся рядом с дампами в файлах `.md5`.

## Ручной запуск бэкапа

Запустить все jobs прямо сейчас:

```bash
make backup
```

Запустить конкретный job:

```bash
make backup-job JOB=01
```

## Восстановление

Интерактивное восстановление:

```bash
make restore
```

Восстановить конкретный файл:

```bash
make restore-file JOB=01 FILE=/backup/file.sql.gz DB_NAME=database
```

`FILE` — путь внутри контейнера, обычно `/backup/...`.
`JOB` — номер блока переменных `DB01`, `DB02`, `DB03` и т.д.
`DB_NAME` — целевая база; если не указана, используется `DB##_NAME`. При `DB##_NAME=ALL` укажи конкретную `DB_NAME`.
Целевая база должна уже существовать. Пример рассчитан на отдельный дамп (`DB##_SPLIT_DB=TRUE`), а не файл сразу с несколькими базами.
Команда выполняет восстановление без подтверждения и может заменить данные целевой БД. Для проверки используй отдельную тестовую базу.
Пароль берётся из `DB##_PASS` внутри контейнера и не печатается в команде.

## Обновление существующей установки

1. Сохрани существующие `backup`, `logs` и `.env`.
   При переименовании останови и удали прежний контейнер без удаления данных, затем перенеси `backup`, `logs`, `.env` и `.env.prod` в папку `nfrastack`.
2. Укажи `DB_BACKUP_VERSION=4.9.2`, замени `USER_DBBACKUP`/`GROUP_DBBACKUP` на `CONTAINER_USER_DBBACKUP`/`CONTAINER_GROUP_DBBACKUP`.
3. Оставь `DEFAULT_MYSQL_SINGLE_TRANSACTION=TRUE` и отключи Zabbix: `CONTAINER_ENABLE_MONITORING=FALSE`.
4. Выполни `make init`, затем `make backup-job JOB=01` для каждого задания и пробное восстановление в отдельную БД.

Не меняй версию на `latest`: это переведёт контейнер на v5 с другим механизмом дампов и восстановления.
В локальной проверке 27.10.2026 версия `5.0.6` не прошла восстановление: пустой BLOB записывался как некорректный SQL `0x`, а `--name` не изолировал восстановление от исходной БД. До исправления и повторного теста используется `4.9.2`.

Документация: [версия 4.9.2](https://github.com/nfrastack/db-backup/tree/4.9.2), [отличия v5](https://nfrastack.com/db-backup/upgrade).

## Команды Makefile

Полный список — `make help`.

| Команда | Действие |
|---|---|
| `make init` | Первичная инициализация: `.env` + pull + up |
| `make up` | Поднять backup-контейнер |
| `make down` | Остановить и удалить backup-контейнер |
| `make restart` | Перезапустить backup-контейнер |
| `make backup` | Запустить все backup jobs прямо сейчас |
| `make backup-job JOB=01` | Запустить один backup job |
| `make restore` | Интерактивно восстановить базу |
| `make restore-file JOB=01 FILE=/backup/file.sql.gz DB_NAME=database` | Восстановить конкретный файл |
| `make logs` | Логи контейнера (последние 100 строк, live) |
| `make ps` | Показать статус контейнера |
| `make config` | Показать итоговый compose-конфиг |
